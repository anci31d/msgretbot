# MsgRetBot

Восстанавливает удалённые **текстовые** сообщения из заданного списка Telegram-групп и супергрупп. Сохраняет последнюю известную редакцию на 24 часа от отправки. Изображения, стикеры, голосовые и прочие медиа пока не восстанавливаются: сохраняются только тип и минимальные метаданные, без файлов и подписей.

## Режимы

- `hybrid`: Telethon читает сообщения и удаления через пользовательский аккаунт; aiogram-бот публикует уведомления.
- `userbot`: чтение и отправка через пользовательский аккаунт Telethon. В этом режиме aiogram не используется для отправки.

Обычный Bot API не предоставляет события удаления сообщений в группах. Поэтому **в обоих режимах нужен пользовательский аккаунт**, состоящий во всех отслеживаемых группах. Для `hybrid` бот также должен быть добавлен в эти группы и иметь право отправки сообщений. Privacy Mode бота не влияет на чтение: читает пользовательский аккаунт.

Поддерживаются обычные группы и супергруппы. Каналы и broadcast-группы отклоняются. Для супергрупп указывайте их актуальный ID вида `-100...`; после миграции обычной группы старый ID больше не используйте. Контекст пока публикуется цитатами, без ссылок на сообщения; для будущих ссылок предусмотрен интерфейс `ContextFormatter`.

## Установка

Python 3.12+ и Linux/POSIX (используется `flock` для защиты сессии от одновременного запуска). Работайте из корня проекта, используя локальную `.venv`:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
cp -n config.example.toml config.toml
```

В `config.toml` укажите реальные отрицательные числовые ID групп или супергрупп и режим. ID супергрупп обычно имеют вид `-100...`. Пример `-123456789` — заглушка, его нужно заменить. Пути БД и сессии разрешены только внутри текущего workspace. Один процесс на одну сессию.

Приложение читает переменные окружения:

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_API_ID` | API ID приложения Telegram |
| `TELEGRAM_API_HASH` | API hash приложения Telegram |
| `TELEGRAM_BOT_TOKEN` | Токен бота, обязателен только для `hybrid` |

Получите API ID/hash своего приложения на `my.telegram.org`, токен — у BotFather. Задайте значения через окружение терминала или менеджер секретов. Для локального запуска экспортируйте эти переменные в окружение shell. Файл `telegram.vars` используется Compose через `--env-file`; локальный Python-процесс сам его не читает. Приложение не загружает `.env` автоматически. Не помещайте секреты в TOML, Git или команды, публикуемые в отчётах.

## Авторизация и запуск

```bash
.venv/bin/python -m msgretbot login --config config.toml
.venv/bin/python -m msgretbot run --config config.toml
```

`login` интерактивно запросит телефон, код Telegram и, при необходимости, пароль 2FA средствами Telethon. Выполните команду самостоятельно в терминале; не передавайте эти данные агенту. Она не отправляет сообщения в группы. Команда `run` использует готовую сессию и не запускает интерактивную авторизацию.

Новые файлы данных создаются с закрытыми правами (`umask 077`). Файл сессии даёт доступ к аккаунту — храните его отдельно от Git и не передавайте третьим лицам. Приложение не меняет права уже существовавших файлов.

## Поведение

При каждом запуске для каждой группы загружаются последние **100 сообщений любого типа**, из которых сохраняются только сообщения моложе 24 часов. Чтение истории не означает восстановление уже отсутствующих в ней сообщений: восстановить можно только заранее сохранённый текст. Живые события буферизуются во время загрузки; более старая редакция из истории не заменяет более новую.

Сохранённые сообщения адресно проверяются после запуска и каждые 30 секунд при наличии соединения — это также закрывает короткие переподключения. Запросы выполняются последовательно с интервалом не менее 0,5 секунды. Неполный ответ, ошибка сети или потеря доступа к группе дают «неизвестно», а не «удалено». При больших объёмах сверка может занимать дольше 30 секунд; мгновенное обнаружение после простоя не гарантируется.

Пример уведомления:

````text
!!! 1984 АЛЕРТ !!!
Сообщение @user удалено:
```
последний сохранённый текст
```
Контекст:
1. alice: более ранняя реплика
2. bob: следующая реплика
3. charlie: ближайшая реплика перед удалённым сообщением
````

Telegram не сообщает достоверно, кто выполнил удаление: это может быть автор или администратор. Упоминание относится к автору. Если username отсутствует, используется имя со ссылкой-упоминанием по ID.

Контекст — последние 10 сохранённых текстовых сообщений перед удалённым в той же группе, в порядке от старых к новым. Наличие этих сообщений в Telegram не проверяется: ранее удалённые сообщения тоже включаются, пока сохранены в БД и не истёк TTL. Авторы могут повторяться или быть неизвестны. Медиа и собственные алерты исключаются. Каждая цитата ограничена 100 символами, включая многоточие при обрезке. Если сообщений меньше 10, показываются доступные; если нет — «Контекст отсутствует». При повторной отправке используется сохранённый снимок контекста.

Каждая часть алерта публикуется отдельным сообщением, без ответа на другие сообщения.

Авторы контекста отображаются по сохранённому username без `@`, со ссылкой вида `https://t.me/username`. Это обычная ссылка на профиль, а не упоминание по ID. Цитаты оформляются кодом, чтобы `@username` внутри них также не становились пингами. Если публичного username нет, выводится обычное имя без ссылки; для имён с символами вне базовых латиницы, кириллицы, цифр и простой пунктуации используется «Участник». Упоминание автора удалённого сообщения в заголовке сохраняется.

Длинные тексты разбиваются на сообщения с учётом UTF-16, HTML экранируется. Исходные Telegram entities не сохраняются. Собственные уведомления не участвуют в контексте и не восстанавливаются. В `hybrid` отправитель должен быть выделенным ботом: все его сообщения исключаются. В `userbot` после потери ответа об отправке собственное уведомление распознаётся по автору и тексту подготовленной очереди.

## Хранение и отказоустойчивость

SQLite использует rollback-журнал TRUNCATE, внешние ключи и версионируемую схему. Отметка об удалении и постановка уведомления в очередь выполняются в одной транзакции. Состояние отправки сохраняется для каждой части длинного уведомления; повторное событие удаления не создаёт дубликат задания.

Общий лимит файла БД сообщений и его SQLite-журнала — **50 МиБ** (52 428 800 байт). Под основной файл выделяется до 24,5 МиБ; остальное зарезервировано под временную копию изменяемых страниц и служебные данные журнала. WAL отключён: его размер может расти независимо от основного файла. `max_page_count` ограничивает рост основного файла, журнал обнуляется после транзакций, временные структуры SQLite хранятся в памяти.

При нехватке места приложение удаляет самые старые сохранённые сообщения небольшими пакетами вместе со связанными заданиями, даже если им меньше суток, и продолжает сохранять новые. Освобождённые страницы переиспользуются, поэтому размер основного файла после удаления может не уменьшаться. Вытеснение отмечается WARNING в логах. Слишком большое одиночное сообщение, которое заведомо не помещается, пропускается с ERROR без удаления истории ради него. Восстановление вытесненных сообщений невозможно. Лимит не включает отдельную сессию Telethon, логи и резервные копии.

Существующая небольшая БД прежней версии автоматически переводится с WAL на TRUNCATE, сохраняя сообщения и очередь. Старый процесс необходимо остановить заранее. Если существующий файл уже превышает 24,5 МиБ (для нестандартного размера страницы предел может быть чуть ниже), приложение безопасно откажется от запуска и запишет ERROR: нужен предварительный перенос/уплотнение БД вне работающего приложения либо запуск с новым файлом после сохранения резервной копии. Автоматически перезаписывать такую БД приложение не будет.

Очистка выполняется при запуске и каждые 30 секунд независимо от сетевых ожиданий. Записи старше 24 часов сразу исключаются из обработки; при очистке удаляются и связанные задания, включая неотправленные уведомления. TTL не продлевается редактированием. Это логическое удаление из таблиц, а не гарантированное физическое стирание SQLite или резервных копий. Исходные сообщения и уже опубликованные уведомления из Telegram приложение не удаляет.

FloodWait/RetryAfter приостанавливает отправку; временные ошибки повторяются через 5 секунд. Ошибки прав/назначения повторяются раз в минуту до истечения TTL. Очередь переживает перезапуск. Userbot использует стабильный `random_id` для повторной отправки одной части. При неопределённом сетевом результате, особенно через Bot API, строго однократная доставка не гарантируется. Неустранимая ошибка фонового обработчика останавливает процесс; запускать повторно можно после устранения причины.

### Массовые удаления

Удаления обрабатываются транзакциями до 100 сообщений с передачей управления между пакетами. Очередь входных событий ограничена 1000 элементами; списки удалений делятся на пакеты до 100 ID. При заполнении приложение ожидает освобождения места, не отбрасывая события. Внутренние буферы Telethon этим лимитом не ограничиваются, поэтому бесконечный поток событий всё ещё может увеличить потребление памяти.

Все подходящие удаления получают отдельные задания. Попытки отправки разделены минимум одной секундой для аккаунта и тремя секундами для одной группы; каждая часть длинного алерта считается отдельно. Задержки сохраняются до обращения к Telegram и действуют после перезапуска. Ожидающая группа не блокирует доставку в другие группы; FloodWait/RetryAfter может приостановить весь аккаунт. Для 4000 одночастных алертов в одной группе потребуется около 3 часов 20 минут или больше. TTL и лимит БД продолжают действовать: просроченные либо вытесненные задания не доставляются.

Сетевые запросы не удерживают общую блокировку обработки событий. Текущая запись защищена от вытеснения по ёмкости во время попытки, но не от истечения TTL. При нехватке ёмкости обработчик делает паузу 60 секунд и повторяет операцию; повреждение БД и программные ошибки не скрываются. Если даже запись задержки невозможна, пауза остаётся только в памяти и может потеряться при перезапуске. После полученного ответа об отправке при ошибке сохранения повторяется запись результата, без повторной публикации в том же процессе; после перезапуска строго однократная доставка по-прежнему не гарантируется.

При обновлении схема SQLite автоматически переводится с версии 1 на 2 с сохранением очереди и подготовленных частей. До обновления остановите старый процесс и сделайте резервную копию данных. Возврат к приложению со схемой версии 1 требует восстановления резервной копии. В логах доступны длительность и размер пакета удалений, заполнение очереди событий и количество ожидающих заданий; детали задержек выводятся на DEBUG.

Сообщения не могут быть восстановлены, если они не были сохранены, старше суток, удалены во время утраты доступа и не поддаются подтверждению либо Telegram не доставил необходимые события. Сессия Telethon хранит служебное состояние и кэш сущностей отдельно от БД сообщений; TTL сообщений не очищает авторизацию аккаунта.

## Логирование

В `config.toml` настройте таблицу:

```toml
[logging]
output = "stdout" # "stdout" or "file"
level = "INFO" # "DEBUG" includes context and reconciliation details
file = "logs/msgretbot.log" # Used only for output = "file"
```

Без этой таблицы используются stdout и INFO. В режиме file вывод идёт в UTF-8-файл с ротацией: основной до 5 МиБ, один архив `.1` до 5 МиБ, суммарно до 10 МиБ. Старый архив заменяется. Новые файлы создаются с правами 0600; путь должен находиться внутри workspace.

Логируются запуск/остановка, подключение, загрузка истории, сохранение и редактирование сообщений, подтверждение удаления и постановка в очередь, попытки и результаты отправки (с ID оригинала, алерта и номером части), повторы/ошибки и очистка БД. DEBUG добавляет выбор контекста, события и сверку. Тексты сообщений, имена, username, токены и данные авторизации не выводятся. На уровнях INFO и выше исключения записываются только по типу. При `level = "DEBUG"` дополнительно выводится полный текст исключения без traceback; настроенные API hash и токен маскируются. Подробные логи сторонних клиентов и SQLite отключены.

После изменения конфигурации перезапустите приложение.

## Docker и Docker Compose

Нужны Docker Engine и плагин Docker Compose. Образ собирается в два этапа на Python 3.14 slim; runtime-зависимости зафиксированы в `requirements.lock`. Внутрь образа попадают только код и зависимости: локальная конфигурация, секреты, сессии, БД и логи исключены из контекста сборки через `.dockerignore`.

Для первого запуска можно авторизоваться непосредственно в Docker (команда ниже) либо использовать **уже авторизованную пользовательскую сессию**. Сначала остановите локальное приложение, чтобы два процесса не открывали одну сессию. На этой же машине каталог `data` подключается напрямую; при переносе на другой сервер скопируйте сессию и при необходимости БД только после остановки исходного процесса. Содержимое сессии не выводите и не отправляйте в Git. Не копируйте живую БД отдельно от её журналов.

Подготовьте файлы (существующий `config.toml` не перезаписывайте):

```bash
mkdir -p data logs
cp -n config.example.toml config.toml
cp -n telegram.vars.example telegram.vars
chmod 600 telegram.vars
```

Если `config.toml` ещё нет, скопируйте `config.example.toml`. В конфигурации оставьте пути внутри монтируемых каталогов:

```toml
database = "data/messages.sqlite3"
session = "data/observer.session"
# If logging.output = "file", use logging.file = "logs/msgretbot.log".
```

При использовании готовой сессии поместите файл `observer.session` в `data/observer.session`. В `telegram.vars` самостоятельно задайте `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` и токен для hybrid (для userbot оставьте пустым). Установите `MSGRETBOT_UID` и `MSGRETBOT_GID` равными UID/GID владельца каталогов `data` и `logs`; узнать свои можно командами `id -u` и `id -g`. По умолчанию используется `1000:1000`. В контейнере этот пользователь должен иметь права записи в оба каталога и в сессию.

```bash
docker compose --env-file telegram.vars config --quiet
docker compose --env-file telegram.vars build
# First deployment only, if there is no authorized session yet:
docker compose --env-file telegram.vars run --rm msgretbot login --config config.toml
docker compose --env-file telegram.vars up -d
docker compose --env-file telegram.vars logs -f --tail 100
```

Команду `login` выполняйте самостоятельно в интерактивном терминале: она запросит телефон, код и при необходимости 2FA. Для уже авторизованной сессии пропустите её. Перед повторной авторизацией остановите сервис: `docker compose --env-file telegram.vars stop`.

Не запускайте `docker compose config` без `--quiet` при передаче настоящих секретов: развёрнутая конфигурация включает переменные окружения. Приложение не загружает `.env`; Compose получает значения из явно указанного `telegram.vars`, который исключён из Git и образа.

Контейнер работает от обычного пользователя, с файловой системой только для чтения, доступом на запись только к постоянным `data`/`logs` и временным `/tmp`. Порты не публикуются: нужен только исходящий доступ к Telegram. `restart: unless-stopped` восстанавливает процесс после сбоя; SIGTERM штатно закрывает соединения и БД. Docker-логи stdout ограничены двумя файлами до 5 МБ каждый. Для просмотра готовности ищите `Recovery service started`; отсутствие этой строки требует проверки конфигурации, сессии, сети и прав каталогов.

Остановка и обновление:

```bash
docker compose --env-file telegram.vars down
git pull --ff-only
docker compose --env-file telegram.vars up -d --build
```

Каталоги `data` и `logs` сохраняются на хосте после удаления контейнера. При обновлении не удаляйте их. Для резервной копии остановите контейнер и скопируйте данные в защищённое место.

Без Compose можно использовать тот же образ, экспортировав нужные переменные в окружение терминала:

```bash
docker build -t msgretbot:local .
docker run -d --name msgretbot --restart unless-stopped --init \
  --user "$(id -u):$(id -g)" --read-only --cap-drop ALL \
  --security-opt no-new-privileges:true --tmpfs /tmp:size=16m,mode=1777 \
  --env TELEGRAM_API_ID --env TELEGRAM_API_HASH --env TELEGRAM_BOT_TOKEN \
  --mount type=bind,source="$PWD/config.toml",target=/app/config.toml,readonly \
  --mount type=bind,source="$PWD/data",target=/app/data \
  --mount type=bind,source="$PWD/logs",target=/app/logs \
  --log-opt max-size=5m --log-opt max-file=2 msgretbot:local
```

## Проверки

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m msgretbot --help
```

Тесты используют временную SQLite и подменённые Telegram-клиенты, не обращаются к Telegram и не отправляют сообщения. Проверки размера включают реальные записи сверх доступной ёмкости, вытеснение очереди, обновление прежней WAL-БД, повторное открытие и размер живого журнала при штатном лимите 50 МиБ. Для временных файлов строго внутри workspace сначала выполните `mkdir -p .cache`, затем `.venv/bin/python -m pytest -q --basetemp=.cache/pytest`.

Для ручной приёмки в отдельных тестовых обычных группах и супергруппах: проверить оба режима, удаление автором и администратором, редактирование перед удалением, автора без username, длинный текст, контекст от разных участников, остановку/возобновление, ограничения отправки и удаление самого уведомления. Публикации агентом допускаются только по отдельному указанию пользователя.

## Участие в разработке

GitHub Actions запускает тесты на Python 3.12/3.14, сборку Docker и офлайн smoke-проверку восстановления.

Установите dev-зависимости командой `.venv/bin/python -m pip install -e '.[dev]'`. Перед pull request запустите тесты и `git diff --check`; изменения поведения сопровождайте тестами и обновлением README. Ошибки описывайте с версией Python/Docker, режимом работы и обезличенными логами. Не прикладывайте токены, сессии, БД и содержимое сообщений.

Локальные `config.toml`, `telegram.vars`, сессии, данные, логи и рабочие заметки исключены из Git. Образцы конфигурации содержат только заглушки. Docker-контекст ограничен исходным кодом и файлами сборки.
