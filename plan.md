# MsgRetBot: согласованный план

## Цель
Отслеживать список Telegram-групп и супергрупп, сохранять сообщения в SQLite на 24 часа и восстанавливать удалённый текст.

## Режимы
- hybrid: Telethon под пользовательским аккаунтом читает события и историю, aiogram-бот публикует уведомления.
- userbot: Telethon под пользовательским аккаунтом читает и публикует.
- Один процесс и один аккаунт наблюдателя. Только явно разрешённые группы.
- Поддерживаются обычные группы и супергруппы (megagroup); каналы и broadcast-группы отклоняются.

## Уведомление
`!!! ШИФРУН АЛЕРТ !!!`, затем «Сообщение @user удалено:», последний известный текст в блоке кода и контекст.
Если username отсутствует — имя с упоминанием по ID. Не приписывать удаление автору.
Контекст: окно из 10 предыдущих сохранённых непросроченных текстовых сообщений, не помеченных удалёнными и не являющихся алертами приложения. Проверить их существование; сначала выбрать ближайшие сообщения разных авторов, затем дополнить ближайшими оставшимися до трёх, даже если автор повторяется. Автор удалённого сообщения допускается. За пределы окна не выходить; медиа в окно не входят. Цитаты до 160 символов, без ссылок, в порядке от ближайшей к более ранним. Если сообщений меньше — доступные; если нет — «Контекст отсутствует».
Длинные уведомления разбиваются без потери текста. Собственные уведомления исключаются из восстановления и контекста.
Каждая часть алерта отправляется ответом на последнее подтверждённо существующее сохранённое сообщение перед удалённым (включая медиа, исключая служебные сообщения и собственные алерты). Проверять привязку при каждой отправке. Если подходящего сообщения нет или Telegram отклонил reply из-за его удаления, отправлять без привязки.
Восстанавливаются только текстовые сообщения; для медиа — тип и минимальные метаданные, без скачивания и восстановления подписей. Для супергрупп используется channel peer и проверка через `GetFullChannelRequest`; ссылки на сообщения пока не добавляются.

## Архитектура и данные
Раздельные Telegram-адаптеры, сервис, форматирование и хранилище. Интерфейсы получения событий, проверки существования, отправки и контекста.
SQLite/aiosqlite, rollback-журнал TRUNCATE и версионируемая схема. Ключ: аккаунт, группа, ID сообщения. События удаления с ID группы строго привязаны к ней: ID сообщений в супергруппах локальны. События без группы сопоставляются только с сохранёнными сообщениями обычных групп аккаунта, исключая супергруппы. После миграции нужен новый ID супергруппы в конфигурации; история старой группы автоматически не переносится.
Общий бюджет БД сообщений и её журналов — 50 МиБ. Основной файл ограничить max_page_count примерно до 24,5 МиБ, резервировать остаток для rollback-журнала и служебного выравнивания; отключить WAL и cache_spill, временные структуры хранить в памяти, обнулять журнал после транзакций. Перед ростом освобождать страницы удалением самых старых сообщений пакетами по 16 вместе с очередью, даже моложе суток; защищать текущую обрабатываемую запись. При SQLITE_FULL откатить транзакцию, освободить старые записи и повторить. Слишком большой одиночный payload пропускать с ERROR без вытеснения истории ради заведомо невместимой записи. Небольшую существующую WAL-БД переводить автоматически; уже превышающую безопасный размер основного файла не изменять и отклонять запуск с диагностикой. Сессия Telethon и логи в эти 50 МиБ не входят.
Хранить автора, исходное время, последний текст, тип, состояние удаления и очередь уведомлений. Транзакционная постановка в очередь, дедупликация, продолжение после перезапуска, задержки и FloodWait/RetryAfter. Строго однократная доставка при сетевой неопределённости не гарантируется.
Секреты, сессии и тексты сообщений не попадают в логи или Git.
Логирование задаётся таблицей [logging] в TOML: output=stdout|file, level=DEBUG|INFO|WARNING|ERROR|CRITICAL, file=путь внутри workspace. По умолчанию stdout/INFO. Файл UTF-8 с ротацией: основной до 5 МиБ и один архив до 5 МиБ, суммарно до 10 МиБ; старый архив заменяется. Логи содержат время, уровень, компонент, сохранение/редактирование сообщений, числовые ID, удаления, очередь, отправку/повторы/ошибки алертов, загрузку истории, сверку и очистку. Тексты, имена, username и секреты не записываются. Детали сверки и контекста — DEBUG. На уровнях INFO и выше исключения выводятся только по типу. В DEBUG дополнительно выводится полный текст исключения без traceback; настроенные API hash и токен маскируются.

## Жизненный цикл
Использовать существующую .venv (обнаружен Python 3.14.8). Конфигурация — режим, ID групп, пути данных; секреты — переменные окружения. .env агент не читает. Отдельная интерактивная авторизация пользователя.
При каждом запуске загрузить последние 100 сообщений каждой группы, сохранить только моложе 24 часов, согласовать с новыми событиями.
При запуске и переподключении адресно сверять сохранённые непросроченные сообщения. Отсутствие в последних 100 не является удалением; ошибка/потеря доступа тоже. Восстанавливать только подтверждённые удаления.
TTL от исходной отправки; правки его не продлевают. Просроченные данные сразу исключаются из запросов. Очистка при запуске и каждую минуту удаляет сообщения и связанные задания, включая неотправленные. Физическое стирание байтов SQLite не гарантируется.

## Проверка и документация
Автотесты: фильтрация групп, удаления без ID группы, правки, контекст (1/2/3 автора, окно 10 текстовых, медиа вне окна), username, форматирование/длина, повторные и пакетные удаления, TTL, очистка очереди, история 100, перезапуск, простой, ошибки доступа, оба отправителя и лимиты Telegram, reply и исчезнувшая цель, stdout/файл/ротация в байтах и отсутствие чувствительного содержимого в логах.
Команда: `.venv/bin/python -m pytest -q`; фактический вывод приложить к отчёту.
README: настройка, запуск, ограничения. Реальные проверки Telegram и публикации — только по отдельному указанию пользователя.
Проверки ёмкости: фактический размер основного файла и живого журнала, вытеснение самых старых и каскад очереди, сохранение новых, слишком большой payload, повторное открытие и переход с WAL. Docker: сборка, pip check, CLI/офлайн smoke под обычным пользователем с read-only rootfs и без сети, проверка Compose без вывода секретов. SIGTERM должен выполнять штатное закрытие ресурсов.
Гарантии ограничены сохранёнными непросроченными сообщениями и возможностями Telegram.
При изменении договорённостей обновлять этот файл. Онлайн-документация и Telegram в ходе планирования не проверены.

## Конкретизация реализации
- Проверка наличия выполняется после запуска и затем каждые 60 секунд: так охватываются и короткие переподключения. Запросы наблюдателя разделены минимум 0,5 секунды; ошибки возвращают UNKNOWN.
- Очередь хранит подготовленные части HTML и номер следующей части. Контекст — снимок на момент подготовки, при повторной отправке заново не собирается.
- Для защиты от старых событий хранится время редакции. Для userbot используется стабильный random_id и распознавание собственных исходящих по автору и подготовленному тексту при потере ACK.
- Ошибки прав отправки повторяются через 60 секунд до TTL; временные — через 5 секунд, FloodWait/RetryAfter — по ответу Telegram.
- Поддерживаемая платформа v1 — Linux/POSIX: flock защищает сессию от одновременного использования. Новые данные создаются с umask 077.
- Общая задержка отправки сохраняется в SQLite и действует после перезапуска. Очередь выбирает задания только для текущего списка разрешённых групп; исключённые группы не получают уведомлений.
- Ответ MTProto об отправке сначала сопоставляется по random_id, затем (если сопоставления нет) по единственному исходящему сообщению с нужными получателем и текстом.

## Развёртывание Docker
- Многоэтапный Dockerfile на Python 3.14 slim; runtime-зависимости зафиксировать в requirements.lock. .dockerignore использует список разрешённых файлов и исключает конфигурацию, секреты, данные, логи и .venv из сборки.
- Compose: один сервис, обычный пользователь (UID/GID по конфигурации окружения), read-only rootfs, read-only config.toml, постоянные bind mounts data и logs, временный tmpfs, без входящих портов, restart unless-stopped, SIGTERM/30 секунд на остановку, ротация Docker stdout-логов.
- Использовать ранее авторизованную локальную сессию через каталог data. Не выполнять авторизацию/запуск настоящего бота агентом. При переносе сначала остановить старый процесс. Не копировать рабочую SQLite отдельно от журналов.
- Секреты передавать окружением или явно указанным пользователем файлом telegram.vars (игнорируется Git и сборкой). Не читать реальные файлы секретов агентом. Документировать запуск/остановку/обновление через Compose и docker run, права каталогов и границы лимита БД.
